# 0019 — Stay on ESP-IDF Build System v1 while v2 is a Technical Preview: the migration is three lines and costs nothing to defer

- **Status:** accepted
- **Date:** 2026-08-21
- **Context:** ESP-IDF v6.0 ships a second, parallel CMake build system, "Build System v2" (`tools/cmakev2/`), alongside the v1 we build on (`tools/cmake/project.cmake`). Its own documentation in the pinned tree opens with an `attention` banner — *"Build System v2 is currently available as a **Technical Preview** intended for **testing and evaluation**. Features, functionality, and performance are **subject to change without notice**, and **production use is not recommended** at this stage."* — and the examples README repeats it (`examples/build_system/cmakev2/README.md`, read in `~/esp/idf/v6.0.2` on 2026-08-21). v2 is genuinely better on paper: Kconfig variables may express component dependencies, the early CMake-script-mode evaluation pass is gone, and components can be written as native CMake. None of that is on the critical path for a firmware whose whole component graph is `main` plus six local components and seven pinned registry components ([ADR 0017](0017-no-radio-in-v1-trimmed-component-set.md)). What *is* on the critical path is that the build is the thing every reproducibility claim rests on ([ADR 0001](0001-toolchain-esp-idf-v6-pinned-environment.md), `CONFIG_APP_REPRODUCIBLE_BUILD=y`, build-twice-and-diff in CI).
- **Decision:** [`firmware/twatch-s3/CMakeLists.txt`](../../firmware/twatch-s3/CMakeLists.txt) stays on **Build System v1** — `cmake_minimum_required(VERSION 3.22)` + `include($ENV{IDF_PATH}/tools/cmake/project.cmake)` + `project(superspectral)` — and the file carries a comment naming this ADR so the choice is visible where it is made. The migration is pre-registered here as a **three-line change**, to be applied in one commit when the trigger fires:

  ```diff
   cmake_minimum_required(VERSION 3.22)
  -include($ENV{IDF_PATH}/tools/cmake/project.cmake)
  -project(superspectral)
  +include($ENV{IDF_PATH}/tools/cmakev2/idf.cmake)
  +project(superspectral C CXX ASM)
  +idf_project_default()
  ```

  (one line repointed, one line given its explicit language list, one line added — `idf_project_default()` creates the default executable from `main` and its transitive dependencies and registers the `flash` / `menuconfig` targets. Components and application code are unchanged.)

  **Trigger to reopen:** v2 leaves Technical Preview — i.e. the `attention` banner is gone from `docs/en/api-guides/build-system-v2.rst` in a v6.x **bugfix** release we are already on or hopping to. Checked as part of step 2 of the [upgrade procedure](../devenv/upgrade-procedure.md) ("read the migration surface before building"), on every hop, and recorded there whether the answer was yes or no. A v7 major is *not* the trigger; a major hop is a separate, larger decision.
- **Alternatives:**
  - *Adopt v2 now, at scaffolding time, so the hop never lands mid-project.* Rejected: Espressif says in as many words that production use is not recommended and that behaviour may change without notice. A build system that may change under a pinned IDF is exactly the thing ADR 0001 exists to prevent. Trigger: the banner disappears.
  - *Keep a second, v2 top-level `CMakeLists.txt` behind a flag, built in CI to stay warm.* Rejected: two build definitions are two chances to diverge, and CI would have to build and diff both configurations for a hop that is three lines when it comes. The cheap version of the same insurance is reading the guide once (bibliography `02 #2`), which is done.
  - *Wait for v7 and skip the v6.x adoption of v2 entirely.* Rejected as a plan, though it may happen by accident: v2's value grows with the component graph, and the graph here is small, but a major hop already carries its own migration surface — adding an untried build system to it is the worse of the two orderings.
- **Consequences:**
  - (+) The build stays on the path that every document we own describes: the Build System guide (`02 #1`), the v6.0 build-system migration guide (`11 #A8`), [pitfalls B1–B22](../devenv/pitfalls.md) and every line of the two `CMakeLists.txt` files are v1 semantics.
  - (+) The hop is a known, bounded quantity rather than an open question, and it is checked on a schedule that already exists.
  - (−) The "three lines" cover the boilerplate only. This project's top-level file also reads `idf_build_get_property(_all_comps BUILD_COMPONENTS)` to append `-fno-analyzer` to registry components (ADR 0017); **`BUILD_COMPONENTS` does not exist in v2 and any attempt to read it is an error** — it must be rewritten around explicit target names / `$<TARGET_EXISTS:tgt>`. Budget the migration as three lines plus that loop.
  - (−) `set(COMPONENTS main)` — the structural radio exclusion of ADR 0017 — is a *deprecated variable* in v2 (`deprecate_variable(COMPONENTS)` in `tools/cmakev2/project.cmake`): ignored, with a warning. The same guarantee comes for free from `idf_project_default()`, but the `sdkconfig-invariants` pre-commit hook greps for that exact literal in [`.pre-commit-config.yaml`](../../.pre-commit-config.yaml) and must be re-pointed in the same commit, or the radio exclusion becomes unasserted.
  - (−) In v2 `sdkconfig` is generated from the Kconfig files of *all discoverable* components, not only those in the build. Promptless symbols we removed by trimming the component set — `CONFIG_ESP_WIFI_ENABLED` (pitfall H11) — will reappear in `sdkconfig` even with no Wi-Fi linked. Config assertions must test the component set, never a symbol's absence.
  - (−) Until the hop, component dependencies cannot be expressed with Kconfig variables and components cannot be written as native CMake. Neither limitation binds a project this small, but it means any component we write is written twice-compatible only by luck; the migration commit must re-check that every component's Kconfig file is named exactly `Kconfig` or `Kconfig.projbuild` (v2 drops v1's custom-name support), which today they are.
  - (−) Deferring guarantees the hop lands mid-project, on a tree with firmware in it, rather than on an empty scaffold.
