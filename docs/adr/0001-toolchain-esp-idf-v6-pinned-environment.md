# 0001 — ESP-IDF v6.0.2 native, pinned: manual clone + per-minor tools root + committed `.envrc`; tilde pins + `dependencies.lock`; no Arduino in any phase; Zephyr rejected; v5.5.5 escape hatch; gate build required

- **Status:** proposed — **accepted when the E1 gate build passes** ([roadmap](../roadmap/documentation-roadmap.md) E1 step 3). If the gate fails, the fallback branch in *Consequences* is executed and recorded here before the status changes.
- **Date:** 2026-08-20
- **Context:** Super Spectral's workload is *PDM capture → FFT → 30–50 Hz graphics* on a LilyGO T-Watch S3 (ESP32-S3-R8 chip-down, 16 MB 1.8 V W25Q128JW flash, 8 MB octal PSRAM, one Knowles SPM1423HM4H-B PDM microphone on GPIO44/47, ST7789V3 over SPI, zero exposed GPIO, BOOT button inside the case). The toolchain must (a) drive the PDM microphone on day one, (b) give a fast float FFT, (c) be reproducible by a third party from a fresh machine, and (d) survive the two-year life of the project without a forced migration. The user's explicit concern is that a badly set-up environment "may cause a lot of troubles later".

  **Host audit (read-only, 2026-08-20; Linux Mint 22.3 / Ubuntu 24.04 base).** Three ESP-IDF trees coexist — `~/esp/esp-idf` (a v5.5-dev *master snapshot*, 2025-05-26, reached by `alias get_idf` in `~/.bashrc`), `~/esp/v5.4.1`, and `~/.espressif/v6.0.1` installed by EIM 0.12.3 — with two competing registries (`esp_idf.json` vs `tools/eim_idf.json`) and ~19 GB on disk. `~/.bashrc` sources ROS 2 Jazzy **unconditionally**, leaking `PYTHONPATH`, `CMAKE_PREFIX_PATH`, `LD_LIBRARY_PATH` and `AMENT_PREFIX_PATH` into every build. `cmake` and `ninja` on `PATH` resolve to STM32CubeCLT's copies under `/opt/st/`. `python3` resolves through a `/usr/local/bin/python3` symlink sitting next to a disabled hand-built interpreter. EIM's activation script exports `IDF_COMPONENT_LOCAL_STORAGE_URL` to a partial local component mirror, which silently short-circuits registry resolution. Two `espidf.constraints.v6.0.txt` files on the host disagree (the 2025 one pins esptool 4.9). The on-disk QEMU is `esp_develop_9.0.0_20240606` (stale); OpenOCD is `v0.12.0-esp32-20260304` (fine). `direnv`, `docker`, `ccache` are present; groups `dialout`+`plugdev`+`uucp`; ModemManager masked; udev already covers `303a:1001/1002`; VS Code has `cpptools` and **not** the Espressif extension. Three catalogued pitfalls are therefore already staged on this machine before a line of firmware exists.

  **Support windows (verified live 2026-08-20).** ESP-IDF has no LTS line: every minor gets a flat 30 months from its own GA date (12 Service + 18 Maintenance). v6.0 (GA 2026-03-20; latest v6.0.2, 2026-06-29) is Service until 2027-03-20 and EOL **2028-09-20** — the only line Espressif currently calls "recommended for new designs". v5.5 (GA 2025-07-21; latest v5.5.5) is already Maintenance and reaches EOL **2028-01-21** — eight months *earlier* despite being older. v6.1-rc1 is two days old.

- **Decision:**
  - **Pin ESP-IDF `v6.0.2`** by tag **and** commit SHA (recorded in [`../devenv/env.lock.md`](../devenv/env.lock.md) at E1). Do not chase v6.1 now; hop after v6.1.1/v6.1.2 (Sep/Oct 2026) through [`../devenv/upgrade-procedure.md`](../devenv/upgrade-procedure.md). Keep **v5.5.5** installed in a *separate* tools root as the compatibility escape hatch; it is never the primary.
  - **Gate the pin** with a 30-minute throwaway build before any feature code: `espressif/esp-dsp==1.8.2`, `lvgl/lvgl==9.5.0`, `espressif/esp_lvgl_port==2.9.0`, `espressif/esp_lcd_touch_ft5x06==1.1.1`, plus one translation unit including `driver/i2s_pdm.h`, `esp_lcd_panel_vendor.h`, `esp_dsp.h`, `lvgl.h`. None of these components declares an upper `idf:` bound, and v6.0's warnings-as-errors + `gnu23` default is the classic third-party breakage point; the gate is the only thing that can invalidate this ADR and it is cheap.
  - **Components**: tilde pins in `main/idf_component.yml` with a committed `dependencies.lock` (`managed_components/` gitignored): esp-dsp `~1.8.2`, lvgl `~9.5.0`, esp_lvgl_port `~2.9.0`, esp_lcd_touch_ft5x06 `~1.1.1`, esp_codec_dev `~1.6.2` (**not** the 2.0.0 betas, which drag in `usb_host_uac`), joltwallet/littlefs `~1.22.3`, lewisxhe/sensorlib `~0.4.1` (MIT; mandatory for the BMA423's Bosch feature blob; `CONFIG_SENSORLIB_ESP_IDF_NEW_API=y`), jgromes/radiolib `~7.7.1` deferred with the radio (ADR 0017). The ST7789 needs **no** component: `esp_lcd_new_panel_st7789()` is in-tree in v6.0 (only `st7789` and `ssd1306` remain in `components/esp_lcd/src/`). `~` expands to patch-only (`>=x.y.z, ==x.y.*`); the lock freezes the bytes.
  - **Python**: `/usr/bin/python3.12` forced at install time with `PATH=/usr/bin:$PATH ./install.sh esp32s3` — there is no `IDF_PYTHON` override; `detect_python.sh` bakes whatever it finds into `pyvenv.cfg`. `python_env` is a disposable cache.
  - **Docker** `espressif/idf:v6.0.2@sha256:0d8c9773d48a327233f9c1d7c654ff0bcf133ae24503ea2e97a57cfe02b8cb67` (index digest captured 2026-08-20; **re-derive before first use**) for CI only, as a job-level `container:`; never `latest` or `release-v6.0` (both rebuilt the day of the audit). Flash from the host, never from the container.
  - **Tooling pins**: clang-format `v20.1.8` (matches esp-clang 20.1.1 on the host); esptool v5 **hyphenated** commands only (`write-flash`, `read-flash`, `flash-id`); `idf-build-apps` 3.0.2; `pytest-embedded` 2.8.1; `esp-idf-sbom` 1.3.1.
  - **Layout**: `~/esp/idf/v6.0.2` (full `--recursive` clone at the tag; **never shallow** — `IDF_VER` comes from `git describe`) and `~/esp/tools/v6.0.2` as `IDF_TOOLS_PATH`; **one tools root per IDF minor**. Each root is ~2 GB and deletable with one `rm -rf`.
  - **Isolation**: activation **only** via the committed `.envrc` (direnv snapshots the environment on entry and restores it on exit): sets `IDF_PATH`/`IDF_TOOLS_PATH`, unsets the four ROS variables and `IDF_COMPONENT_LOCAL_STORAGE_URL`, prepends `/usr/bin` to `PATH`, sources `export.sh`, and asserts `idf.py --version` = v6.0.2. No alias, no `export.sh` in `.bashrc`.
  - **Editor downstream of the shell**: `.clangd` with `CompilationDatabase: build` and `Remove: [-m*, -f*]` (the Xtensa-only flags make clangd refuse to index); `build/compile_commands.json` from `idf.py`; MS IntelliSense disabled; **no Espressif VS Code extension** (v2.1.0 removed its own path settings in favour of EIM-only discovery).
  - **No Arduino in any phase.** `espressif/arduino-esp32` never enters `idf_component.yml`, `components/`, or the link line. LilyGoLib and arduino-esp32 are read-only artefacts: the schematic PDF, the prebuilt factory `.bin` flashed once in E2 to prove the hardware, and MIT source read as a register reference. Pin macros are derived from the schematic and LilyGoLib's MIT headers, never from `arduino-esp32/variants/` (LGPL-2.1).
  - **Host cleanup only after the new layout builds and flashes** (E1 step 6): repoint/delete `get_idf`, guard the ROS source behind a function, remove the three old trees (~19 GB) confirming each.

- **Alternatives:**
  - *Zephyr RTOS (the swarm house default), now.* Rejected for this project. Four independently verified facts: `boards/lilygo/twatch_s3/twatch_s3-pinctrl.dtsi` defines five pinctrl groups (`i2c0/i2c1/spim2/spim3/ledc0`) and **zero** I2S entries; `drivers/i2s/i2s_esp32.c` implements **standard mode only** (`i2s_hal_std_set_rx_slot()`; grep `pdm` → 0 matches, and the `espressif,esp32-i2s` binding has no mode property); `drivers/audio/` carries DMIC drivers for Ambiq, Infineon, NXP, ST, Nordic and `native_sim` — **nothing for Espressif**, no open PR, no out-of-tree driver; the board documentation states **"Not actively maintained"** with no `MAINTAINERS.yml` entry. Add the open PSRAM bug (zephyr#98137, allocation hangs when called from a thread — which blocks a PSRAM-backed waterfall), the absence of esp-dsp as a Zephyr module (ANSI-C FFT ≈ 1.8× slower), and the 20 MHz `mipi-max-frequency` in the shipped DTS (~21 fps). Time to first spectrogram: weeks (write `dmic_esp32.c` over `i2s_hal_pdm_*`) vs days. **Revisit trigger:** an upstream Espressif DMIC driver lands, or a deliberate decision to write and upstream `dmic_esp32.c` (which would also serve swarm's out-of-tree T-Beam board) — noted as shared future work, off both projects' critical paths (roadmap Q45).
  - *ESP-IDF v5.5.5 as primary ("older = safer").* Rejected: Maintenance-only since 2026-07-21, EOL 2028-01-21 — eight months before v6.0. Greenfield code pays nothing for v6.0's legacy-driver removals (the PDM path uses `driver/i2s_pdm.h` either way). Kept as the escape hatch.
  - *ESP-IDF Installation Manager (EIM) as the install route.* Rejected: 0.x, manifest schema changed twice in 15 months (`idf-env.json` → `esp_idf.json` → `eim_idf.json`), apt line uses `[trusted=yes]`, and its activation script is the source of the `IDF_COMPONENT_LOCAL_STORAGE_URL` hazard on this very host. A git tag plus an explicit tools path is the only route whose entire state fits in two committed lines and reproduces on CI.
  - *Espressif VS Code extension as environment owner.* Rejected: keeps its own path settings that do not track the shell; v2.1.0 (2026-05) deleted `idf.espIdfPath`/`idf.toolsPath` and delegates discovery to EIM. Keeping the editor downstream of `idf.py` → `compile_commands.json` makes terminal, editor and CI builds identical. May be installed later purely for its JTAG debug UI, never to own the build.
  - *Arduino-as-an-ESP-IDF-component for a "proven-drivers" bring-up phase.* Rejected: LilyGoLib cannot be an IDF component at all (no `CMakeLists.txt`/`Kconfig`/`idf_component.yml`; `library.json` declares `"frameworks": ["arduino"]`), so a hybrid means writing a throwaway Arduino shim. `arduino-esp32` 3.3.11 is "based on ESP-IDF v5.5.5" (its `<6.2` manifest bound hides `rules:` that exclude components on IDF 6), forces `CONFIG_FREERTOS_HZ=1000`, hidden-`select`s `WIFI_ENABLED`/`ETHERNET`/`LWIP_SO_RCVBUF`, squats core 1 with an 8 KB loop task and a priority-24 serial task, and incurs the LGPL-2.1 §6a relink obligation on every shipped binary. SensorLib and RadioLib provide the same driver lineage under MIT, Arduino-free; `esp_lcd`/`i2s_pdm`/`i2s_std` are in-tree. Net pure-IDF driver gap: zero.
  - *PlatformIO.* Rejected: a second build front-end wrapping `idf.py` with its own tool cache and platform pins, lagging ESP-IDF releases; on a host that already has two competing IDF registries, a third is the wrong direction. Its udev rules already present here are harmless and are left alone.

- **Consequences:**
  - (+) The microphone works on day one (`driver/i2s_pdm.h`, hardware PDM→PCM on I2S0); esp-dsp's `_aes3` float kernels are one `add-dependency` away; built-in USB-Serial-JTAG debugging with no adapter; the platform is vendor-maintained for the life of the project (EOL 2028-09-20).
  - (+) The whole environment is expressible as two committed lines (`IDF_PATH`, `IDF_TOOLS_PATH`) plus `.envrc`, `dependencies.lock` and `env.lock.md`; a third party reproduces it from a fresh Ubuntu 24.04 machine or the digest-pinned container; `CONFIG_APP_REPRODUCIBLE_BUILD=y` + build-twice-and-diff proves a field binary came from a commit.
  - (+) Every remaining dependency is MIT or Apache-2.0; the firmware stays reusable and the split licence of ADR 0004 holds without exceptions.
  - (−) **The v6.1 hop is budgeted, not optional**: Service on v6.0 ends 2027-03-20; the hop (new tree + new tools root, `idf.py size --diff`, golden-vector diff, `sdkconfig.rename*` review, HIL pass, one reviewed bump commit) is scheduled for Q4 2026 and costs a session.
  - (−) **Review debt** lands on us: v6.0 makes warnings errors by default and defaults to `gnu23`/`gnu++26` and PicoLibc; third-party components that break under those defaults are our problem to patch or pin (`esp_lcd_touch_ft5x06` must be checked for `driver/i2c_master.h` vs the legacy `driver/i2c.h`, which `esp_lcd` no longer accepts — roadmap threshold T10).
  - (−) No Espressif extension means the JTAG debug UI is a hand-written `cppdbg` launch config with OpenOCD as a `preLaunchTask`.
  - (−) A per-minor tools root costs ~2 GB each time; two roots (v6.0.2 + v5.5.5) are the steady state.
  - (−) Diverges from swarm's stated Zephyr/west house style; the shared-upstream idea (Q45) stays parked.
  - (−) Peripheral drivers that Zephyr would have given for free must be written or adopted: an AXP2101 driver (~300 lines over `i2c_master_bus_handle_t`, with SensorLib's `PmicAXP2101` as the schedule-pressure fallback), BMA423 via SensorLib, touch via `esp_lcd_touch_ft5x06` (no chip-ID gate; FocalTech register map shared with the FT6336U at 0x38).
  - (−) Security fixes arrive only through deliberate bumps of the tag and the lock; a calendar reminder for Espressif's EOL advisories is part of the procedure.
  - (−) The E1 cleanup deletes ~19 GB of old toolchains irreversibly; it is sequenced last and each deletion is confirmed by the user. Nothing in those trees is source.
  - **Fallback branch if the gate fails:** record the exact failure text here; install v5.5.5 in `~/esp/idf/v5.5.5` + `~/esp/tools/v5.5.5`; repeat the gate; switch `.envrc`; accept EOL 2028-01-21 and schedule the v6.x migration for 2027. `CONFIG_COMPILER_DISABLE_DEFAULT_ERRORS=y` is permitted only as a crutch while fixing a single component, then removed.
